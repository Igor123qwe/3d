## 1. Что есть: функции и потоки

### Модель данных (`types.ts`)
- `Plan { version: 1, name, walls, openings, furniture, rooms, dims, settings{grid}, underlay?, electric? }` — все размеры в см, углы в градусах (`types.ts:1`, `types.ts:185-197`).
- `Wall { a, b, thickness, locked? }` — отрезок с толщиной, высоты нет (`types.ts:8-15`).
- `Opening { kind: door|window|doorway, wallId, t 0..1, width, hinge, side }` — без высоты, подоконника, типа полотна (`types.ts:19-30`).
- `Furniture { type, x, y, w, d, rot, h?, flip?, label?, note?, color?, model?, electric?, product? }` — электрика **является мебелью** с полем `electric: ElectricPoint { kind, why, height, feeds?, power? }` (`types.ts:43-110`).
- `RoomMeta { id, anchor, name, floor }` — комната не хранится, а **выводится** из замкнутого контура стен и опознаётся по якорной точке; смысл комнаты (кухня/санузел) — только строка `name` (`types.ts:131-139`).
- `DimensionLine` с привязкой концов к оси/грани/концу стены (`types.ts:146-160`).
- `ElectricSettings { allottedKw, stove, ceiling }` (`types.ts:113-120`).

### Поток «стены → комнаты» (`rooms.ts`)
1. `splitWalls` режет стены во всех пересечениях и Т-примыканиях, допуск 0.75 см (`rooms.ts:20,36-62`).
2. `detectFaces` строит планарный граф, обходит грани, оставляет внутренние (площадь отриц., ≥ 0.3 м²) (`rooms.ts:70-140`).
3. `buildRooms` очищает шипы, считает внутренний контур офсетом на полтолщины, площадь по внутренним граням, подбирает метаданные по якорю, новым даёт имя по площади (`rooms.ts:171-219`).
4. В `PlannerPage` результат мемоизирован по `[plan.walls, plan.rooms]`, новые метаданные записываются в план тихо (`PlannerPage.tsx:338-343`).

### Операции (`ops.ts`, `walledit.ts`, `dims.ts`)
- Чистые функции `Plan → Plan`: стены, прямоугольник без дублей, проёмы с прижимом внутрь стены, мебель, подложка, масштабирование всего плана, локальная правка участка (`ops.ts:21-430`).
- «Как в The Sims»: прямая из соосных кусков, сдвиг поперёк, участок с перемычками, склейка `normalizeWalls`, замки `guardLocks/touchesLocked`, разрывы `findGaps/closeGaps` (`walledit.ts:46-628`).
- Размеры следуют за стенами: `followDims` вызывается историей на каждую правку (`dims.ts:133-150`, `store.ts:34`, `PlannerPage.tsx:252`).

### Проверки (`checks.ts:100-334`)
1. Пересечения мебели со стенами и между собой (SAT, `convexOverlap`).
2. Зоны эргономики из `catalog.clearance` (46 предметов с зонами).
3. Дверь задевает мебель (сектор открывания).
4. Комната без двери/проёма; жилая без окна (только точные имена из `LIVING_ROOMS`).
5. Кровать: изголовье не у стены, под окном, ногами к двери.
6. Рабочий треугольник кухни (4–8 м, стороны 1.2–2.7 м), плита вплотную к холодильнику.
7. Электрика: нет светильника в комнате, розетка в 60 см от ванны, выключатель внутри санузла, у кровати нет розетки в 2 м.
8. Телевизор — диван 1.8–3.3 м.
9. Разрывы стен ≤ 30 см (`findGaps`), не больше 10 штук.

### Электрика
- `electrics.ts` — авторасстановка: свет по якорю комнаты (+второй при > 18 м²), выключатели у двери со стороны ручки (санузел — снаружи), розетки у мебели (`wantsFor`), добор до нормы (`fillOutlets`), умный дом, щит (`electrics.ts:348-499`). Запреты: зоны ванны 60 см, газовая плита 50 см, мойка 30 см (`electrics.ts:213-222`).
- `electricplan.ts` — инженерная часть: группы (`groupPoints`), защита (`protection`), спрос (`demandOf`), трассы (`routeOf`), щит/модули, ведомость (`billOfMaterials`), замечания по нормам (`electricIssues`), CSV (`designCsv`) (`electricplan.ts:205-488`). Пересчёт на каждую правку через `useMemo` (`PlannerPage.tsx:1846`).

### Сохранение
- Автосохранение в `localStorage['boop.planner.plan.v1']` через 400 мс после любого изменения; при переполнении — повтор без `underlay.original`, затем тост (`PlannerPage.tsx:71,352-372`).
- Настройки UI в `boop.planner.ui.v1` (`PlannerPage.tsx:375-379`).
- Файл: `downloadJson` / `readPlanFile` → `normalizePlan` (`exporters.ts:16-18,63-78,93-172`).
- Ссылка: JSON без подложки → deflate-raw → base64url в `#plan=` (`share.ts:20-51`); открытие с подтверждением, если в браузере уже есть план (`PlannerPage.tsx:459-470`).

### История (`store.ts`)
- Снимки всего `Plan`, глубина 100 (`store.ts:10`), `apply` (в историю), `preview/endPreview/cancelPreview` (перетаскивание — один шаг), `silent` (без истории), `replace` (сброс истории) (`store.ts:40-100`).

### Экспорт
- JSON, SVG (сериализация скрытого `<svg>` со `Scene`), PNG (SVG → canvas, масштаб `z=2` px/см), CSV электрики (`PlannerPage.tsx:678-710,3306-3307,2956`; `exporters.ts:25-61`).

### Тесты и CI
- 34 файла, **575 тестов, все зелёные, 6.3 с** (`npx vitest run`, 2026-09-25 22:12).
- CI (`.github/workflows/ci.yml`): `tsc --noEmit`, `npm test`, `npm run build` на push/PR. Pages (`pages.yml`) — сборка и деплой на push в `main`.
- Бенчмарк распознавания `tools/bench.mjs` — 14 планов в `bench/plans`, запускает dev-сервер + playwright-core локально.

## 2. Что сделано хорошо

- **Чистое ядро.** Все операции — функции `Plan → Plan` без побочных эффектов (`ops.ts`, `walledit.ts`, `dims.ts`, `electricplan.ts`), поэтому 575 тестов работают без DOM и за 6 секунд. Это уровень Sweet Home 3D по тестируемости и выше, чем у большинства браузерных планировщиков.
- **История с предпросмотром.** `preview/endPreview` даёт один шаг undo на перетаскивание, `follow` пересчитывает привязанные размеры на каждом шаге и при undo (`store.ts:34-64`, тесты `store.test.ts`, `dims.test.ts:39-73`).
- **Защитная нормализация входа.** `normalizePlan` проверяет каждую запись из файла/ссылки: нечисловые координаты, нулевые габариты, проёмы на несуществующих стенах, мусор вместо замка (`exporters.ts:80-172`, `share.test.ts:56-90`).
- **Электрика с явными нормами и объяснениями.** Каждая точка помнит `why` и высоту; замечания ссылаются на ПУЭ 7.1, ГОСТ Р 50571.7.701, СП 31-110-2003 (`electricplan.ts:6-12,405-468`). Ни один из перечисленных лидеров, кроме Remplanner, электрику как проект не считает; расчёт групп/автоматов/сечений/ведомости — уникален для браузерных планировщиков.
- **Шаблоны как контракт качества.** Тест гарантирует, что стартовые планировки не дают ни ошибок, ни предупреждений проверки (`checks.test.ts:156-165`) и что электрика по нормам не порождает замечаний (`electricplan.test.ts:31-36`).
- **Замки и разрывы.** `guardLocks` не даёт задеть зафиксированную стену даже через соседнюю (`walledit.ts:478-509`), `findGaps` объясняет, почему комната пропала (`checks.ts:330-332`).
- **Стойкость к переполнению localStorage.** Повторная попытка без исходного фото и понятный тост (`PlannerPage.tsx:355-368`).

## 4. Риски

### Производительность
- **Пересчёт всего на каждый кадр.** `runChecks` (`PlannerPage.tsx:344`) и `designElectrics` (`1846`) зависят от `plan` целиком: каждый `preview` при перетаскивании запускает SAT по всем парам «мебель × мебель» и «мебель × стена» (`checks.ts:114-128`) и перекладку групп/трасс с поиском ближайшего соседа O(P²) на группу (`electricplan.ts:146-172`). При 100 предметах и 60 стенах это ~10 тыс. `convexOverlap` за кадр — на десктопе незаметно, на телефоне при 60 fps — риск рывков.
- **`detectFaces` квадратичен**: `splitWalls` O(W²) (`rooms.ts:36-62`), `vertexId` — линейный поиск по всем вершинам на каждую вставку (`rooms.ts:73-77`). При 500 стенах (распознанный сложный план) — ~10⁶ операций на пересчёт; терпимо, при 2–3 тыс. — секунды.
- **Автосохранение сериализует подложку.** `JSON.stringify(plan)` с data-URL на сотни КБ–МБ через 400 мс после каждой правки (`PlannerPage.tsx:352-372`); на мобильном это блокировка главного потока на десятки мс плюс износ квоты.
- **Сравнение метаданных через `JSON.stringify`** на каждый рендер (`PlannerPage.tsx:342`) — дешево, но растёт с числом комнат.

### Надёжность
- **S1/S2 — тихая потеря данных** при штатном сценарии «поработал, закрыл вкладку, открыл».
- **Нет защиты от гонок между вкладками** (S4) и от устаревшей схемы (D5).
- `window.confirm`/`window.prompt` для замены плана из ссылки и калибровки (`PlannerPage.tsx:466,818`) — блокирующие, в Telegram WebView иногда не показываются.
- `decodePlan` без проверки `DecompressionStream` (S6).
- Три расходящихся классификатора комнат (D4) — правки норм в одном месте не попадают в другие.
- Замечание о перегрузке ввода на стоковом шаблоне (E4) подрывает доверие к остальным замечаниям.

## 5. Идеи: что сделать лучше (кратко)

1. **Починить `normalizePlan`**: переносить `electric` и `underlay.original`, валидировать `floor`, `electric.kind`, `feeds`; добавить тест «шаблон + electric + underlay → normalize → deep-equal». Это один вечер и закрывает blocker.
2. **Единый классификатор комнат** `roomKind(name): 'living'|'bedroom'|'kitchen'|'wet'|'hall'|'storage'|'outdoor'` в `catalog.ts` (или явное поле `RoomMeta.kind` с выбором в свойствах комнаты), использовать в `checks`, `electrics`, `electricplan`, `furnish`.
3. **Высоты в модели**: `Plan.ceiling` как источник истины для 3D и электрики; `Wall.height?`, `Opening.sill?/height?`; затем `Plan.levels[]` — по образцу Sweet Home 3D (уровень = высота + набор стен/мебели).
4. **Нормативные проверки помещений**: минимальные площади/ширины СП 54.13330, сквозной проход от двери (растровая или графовая проверка свободного пути ≥ 70–90 см), дверь санузла не в кухню/жилую; показывать «ещё N замечаний» вместо тихой обрезки на 80.
5. **Электрика**: поле `controls: string[]` у выключателя и авто-привязка к светильникам комнаты; трассировка по осям стен (граф стен + коридоры) вместо «локтя»; трёхфазный ввод при ≥ 15 кВт с раскладкой групп по фазам; коэффициенты спроса по СП 256 (таблица 7.1) — чтобы шаблон не давал перегрузку; слаботочка как отдельный слой; удалить `electricSpec/cableEstimate`.
6. **Экспорт**: PDF в масштабе 1:50/1:100 со штампом, масштабной линейкой и листами «план», «мебель», «электрика» (svg → pdf на клиенте); `@media print`; простой DXF (LINE/LWPOLYLINE/TEXT — достаточно для передачи в CAD); отдельный лист «щит» (однолинейная схема из `circuits`).
7. **Сохранение**: список проектов в IndexedDB (план и картинки отдельными записями), `storage`-слушатель для второй вкладки, `version` + реестр миграций, короткая ссылка через `api/` (уже есть серверные функции), экспорт `original` в JSON по желанию.
8. **История**: склеивать подряд идущие сдвиги одного объекта в один шаг (по таймеру 300 мс), сделать замок/прозрачность подложки и имя плана отменяемыми (или явно объяснить, что нет), сбрасывать `dragStart` в `apply`.
9. **Тесты/CI**: один smoke-e2e (playwright + `npx playwright install chromium`): открыть шаблон → сдвинуть стену → F5 → те же стены и настройки → экспорт PNG не пустой; покрытие с порогом для `src/planner/*.ts`; `needs: build` в `pages.yml`; eslint + prettier; обновить README:271.
